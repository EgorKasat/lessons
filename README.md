## 1. Введение

**Принципы разработки ПО** — это набор проверенных правил и рекомендаций,
которые помогают создавать код, который легко:

- читать 👀
- поддерживать 🔧
- тестировать 🧪
- расширять ➕
- переиспользовать ♻️

Принципы — не догма, а ориентиры. Их цель — снизить **сложность** и
**стоимость сопровождения** программных систем.

---

## 2. KISS — Keep It Simple, Stupid

> «Не усложняй там, где можно сделать проще.»

**Суть:** самое простое решение, которое работает, — обычно лучшее.

❌ Плохо:
```python
def is_even(n):
    return True if n % 2 == 0 else False
```

✅ Хорошо:
```python
def is_even(n):
    return n % 2 == 0
```

---

## 3. DRY — Don't Repeat Yourself

> «Каждая единица знания должна иметь единственное представление в системе.»

**Суть:** дублирование логики → дублирование багов и правок.

❌ Плохо:
```python
area1 = 3.14 * r1 * r1
area2 = 3.14 * r2 * r2
```

✅ Хорошо:
```python
def circle_area(r):
    return math.pi * r ** 2
```

⚠️ **Важно:** DRY — про *знания*, а не про буквально одинаковый код.
Преждевременное объединение похожего кода может нарушить KISS.

---

## 4. YAGNI — You Aren't Gonna Need It

> «Не реализуй то, что не требуется сейчас.»

**Суть:** не пиши функциональность «на будущее» — оно может никогда не
наступить, а поддержка уже стоит времени.

❌ Плохо: добавить 10 параметров в функцию «на всякий случай».

✅ Хорошо: реализовать только нужное сейчас.

```python
# ❌ Плохо
def create_user(name, age, email=None, phone=None,
                address=None, nickname=None, avatar=None):
    ...

# ✅ Хорошо
def create_user(name, age, email):
    ...
```

## 5. SOLID

Аббревиатура из 5 принципов ООП-дизайна (Роберт Мартин).

### S — Single Responsibility Principle (SRP)

У класса должна быть **одна причина для изменения**.

```python
# ❌ Плохо: класс делает и то, и другое
class Report:
    def calculate(self): ...
    def save_to_pdf(self): ...

# ✅ Хорошо: разделение ответственности
class ReportCalculator:
    def calculate(self): ...

class PdfExporter:
    def export(self, report): ...
```

### O — Open/Closed Principle (OCP)

Классы открыты для **расширения**, но закрыты для **изменения**.

```python
class Shape:
    def area(self): ...

class Circle(Shape):
    def area(self):
        return math.pi * self.r ** 2

class Square(Shape):
    def area(self):
        return self.side ** 2
```

### L — Liskov Substitution Principle (LSP)

Подклассы должны **заменять** базовый класс без поломки логики.

```python
# ❌ Нарушение LSP
class Rectangle:
    def set_width(self, w): self.w = w
    def set_height(self, h): self.h = h

class Square(Rectangle):
    def set_width(self, w):
        self.w = self.h = w   # меняет и высоту — сюрприз для клиента
```

### I — Interface Segregation Principle (ISP)

Не заставляй клиента зависеть от методов, которые он не использует.
Лучше много **маленьких** интерфейсов, чем один **большой**.

```python
# ❌ Плохо
class Machine:
    def print(self): ...
    def scan(self): ...
    def fax(self): ...

# ✅ Хорошо
class Printer:
    def print(self): ...

class Scanner:
    def scan(self): ...
```

### D — Dependency Inversion Principle (DIP)

Зависимости от **абстракций**, а не от конкретных реализаций.

```python
# ❌ Плохо
class Order:
    def __init__(self):
        self.db = MySQLDatabase()

# ✅ Хорошо
class Order:
    def __init__(self, db: Database):  # абстракция
        self.db = db
```

## 6. Separation of Concerns (SoC)

> Разделяй программу на части, каждая из которых отвечает за **отдельный
> аспект** (UI, бизнес-логика, доступ к данным).

Классический пример — **MVC**, **MVVM**, **слоистая архитектура**.

```
[ UI ] → [ Domain Logic ] → [ Data Access ] → [ DB ]
```

## 7. Инкапсуляция

> Скрывай детали реализации, предоставляй **чистый интерфейс**.

```python
class BankAccount:
    def __init__(self):
        self.__balance = 0          # приватное поле

    def deposit(self, amount):      # публичный метод
        if amount <= 0:
            raise ValueError("Сумма должна быть положительной")
        self.__balance += amount

    @property
    def balance(self):
        return self.__balance
```

## 8. Слабая связанность и высокая связность

| Характеристика       | Значение                                      |
|----------------------|-----------------------------------------------|
| **Low coupling**     | Модули мало зависят друг от друга             |
| **High cohesion**    | Внутри модуля — только логически близкое      |

✅ Цель: **минимум зависимостей между модулями**, **максимум связности внутри**.

```python
# ❌ Сильная связанность
class OrderService:
    def create(self):
        db = MySQLDatabase("localhost", "root", "1234")  # жёсткая привязка
        db.insert(...)

# ✅ Слабая связанность
class OrderService:
    def __init__(self, db):     # зависимость передаётся извне
        self.db = db

    def create(self, order):
        self.db.insert(order)
```

## 9. Композиция над наследованием

> Предпочитай **включать** поведение, а не **наследовать** его.

```python
# ❌ Глубокое наследование
class Animal: ...
class FlyingAnimal(Animal): ...
class SwimmingFlyingAnimal(FlyingAnimal): ...  # 💥 взрыв иерархии

# ✅ Композиция
class Duck:
    def __init__(self):
        self.fly_behavior = FlyWithWings()
        self.swim_behavior = SwimInWater()
```

## 10. Принцип наименьшего удивления (POLA)

> Код должен вести себя **предсказуемо** для читателя.

- Функция `get_user()` не должна удалять пользователя.
- Флаг `verbose` не должен менять формат вывода.
- Сортировка `sort()` в Python сортирует **на месте**, а `sorted()`
  возвращает новый список — это ожидаемое поведение.

```python
# ❌ Удивляет
def get_user(user_id):
    db.delete(user_id)   # 🤯 почему удаляет?
    return None

# ✅ Ожидаемо
def get_user(user_id):
    return db.find(user_id)
```

## 11. Fail Fast

> Ошибку лучше обнаружить **как можно раньше**.

```python
def divide(a, b):
    if b == 0:
        raise ValueError("Деление на ноль")
    return a / b
```

Плюсы:

- понятные стектрейсы,
- меньше «тихих» багов,
- проще отладка.

## 12. Тестируемость

Хороший код легко покрывается тестами.

Принципы:

- маленькие функции с одной задачей,
- зависимости через параметры (DI),
- отсутствие глобального состояния,
- детерминированность.

```
      ┌────────────┐
      │ Unit tests │  ← быстрые, изолированные
      └────────────┘
      ┌────────────────┐
      │ Integration    │  ← проверка связок модулей
      └────────────────┘
      ┌─────────────────────┐
      │ End-to-End (E2E)    │  ← проверка всей системы
      └─────────────────────┘
```

```python
def test_circle_area():
    assert circle_area(2) == pytest.approx(12.566, rel=1e-3)
```

## 13. Читаемость кода

> «Код читают в 10 раз чаще, чем пишут.»

Правила:

- осмысленные имена (`user_count`, а не `x`);
- короткие функции;
- комментарии — про **почему**, а не **что**;
- единый стиль (PEP 8, ESLint, gofmt и т.д.);
- избегай «магических чисел» → именованные константы.

```python
# ❌ Плохо
if u.s >= 18 and u.s <= 65:
    ...

# ✅ Хорошо
WORKING_AGE_MIN = 18
WORKING_AGE_MAX = 65

if WORKING_AGE_MIN <= user.age <= WORKING_AGE_MAX:
    ...
```

## 14. Итоговая шпаргалка

| Принцип                | Кратко                                          |
|------------------------|-------------------------------------------------|
| **KISS**               | Делай проще                                     |
| **DRY**                | Не дублируй знания                              |
| **YAGNI**              | Не делай «на будущее»                           |
| **SRP**                | Один класс — одна ответственность               |
| **OCP**                | Открыт для расширения, закрыт для изменения     |
| **LSP**                | Подкласс заменяет родителя без сюрпризов        |
| **ISP**                | Много маленьких интерфейсов > один большой      |
| **DIP**                | Зависи от абстракций, не от реализаций          |
| **SoC**                | Разделяй ответственности по слоям               |
| **Инкапсуляция**       | Скрывай детали реализации                       |
| **Low coupling**       | Слабая связанность модулей                      |
| **High cohesion**      | Высокая связность внутри модуля                 |
| **Композиция > насл.** | Включай поведение, а не наследуй                |
| **POLA**               | Код должен удивлять как можно меньше            |
| **Fail Fast**          | Падай рано и громко                             |
| **Тестируемость**      | Код должен легко покрываться тестами            |
| **Читаемость**         | Код — для людей, не для машин                   |

## 🎯 Вывод

Принципы разработки ПО — это **инструменты**, а не правила ради правил.
Их задача — сделать систему:

- **простой** (KISS, YAGNI),
- **гибкой** (SOLID, OCP, DIP),
- **поддерживаемой** (DRY, SoC, читаемость),
- **надёжной** (Fail Fast, тесты).

> Хороший код — это код, который **легко изменить**.
